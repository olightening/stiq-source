Mailbox flood protection

Caps on credential-exchange requests (enrollment + token draws) the relay forwards to your organizer mailbox. These requests are anonymous, so — like DMs — they can only be capped globally and per-connection. They shield the single-threaded mailbox from a request flood. A real member sends about one request per connection, so the per-connection cap can be tight. 0 = unlimited. Published with the limits below.

Posting Tokens

Blind posts spend an anonymous token so the relay can limit spam without seeing who posted. This sets how many tokens each member may draw per epoch (1 day) — the anti-spam cap for blind posting. Tokens are blind-signed, so you can't link one to a member and there is no revoke: this only controls how many are handed out. Saved on this box (not published to the relay); takes effect immediately.

Token & sealing activation

Turn the community-wide token & encryption features on or off. These are relay switches (not published to Nostr), flipped live here — the relay hot-reloads within a second. One-way for members: a member whose app hasn't updated yet will break when you enable a feature they can't speak, so only enable each one after your members have updated.

Fleet key-sync (stiq:token-keys)

Every purpose key (post / read / picture / audio / space-write) is re-broadcast to the whole community at startup and on every flip below, so already-enrolled members converge without re-inviting — this is the fix for the "swk" incident (a key added after members joined never reaching them). This line reports whether that broadcast actually reached the relay.

Space tokens — channels, groups & DMs

Requires an anonymous token for every channel message, group post, and DM — the same anti-spam brake feed posts already use, extended to every space. Messages stay signed by the member (roles & names unaffected); the token just proves they paid the spam price. Posting stays uncensorable.

Media token domains — pictures & audio

Meters pictures and audio on their own token budgets (separate from text), so you can price/limit media independently. Soft: updated apps opt in automatically; older apps keep paying from the normal post budget, so this one does not break anyone.

Content encryption — censorable reads

Seals post bodies so only members who spend a read token can decrypt them — and lets you stop a specific member from reading (revoke them under Read access). Posting stays uncensorable; the most this does to a writer is nothing. Enabling flips the relay advertisement and this box's read-auth enforcement together.

Read access

Stop a specific member from reading. When read-auth enforcement is on (STIQ_READ_AUTH=1) and content is sealed, a revoked member gets no fresh read tokens, so cannot decrypt new posts. Posting is never affected — the most a mod can do to a poster is ban, which only moves their posts to the mod log. Revoking is purely organizer-side (nothing is published); reinstating restores reading. Identify the member by their npub (visible in the app / mod console).

Rising Algorithm

Tune the feed's Rising sort. A post's score adds up four independent signals — time, votes, comments, and all-time score — then scales the total by the post's type and length. Every weight is 0 = off, so any signal can be switched out of the algorithm entirely. All four are measured on the same scale, so the weights are directly comparable: at equal weight, a vote and a comment count the same. Publishing signs a kind-30078 stiq:ranking event applied live in every app.

( time×freshness + votes×log(1+recent votes) + comments×log(1+recent commenters) + score×log(1+score) ) × type × ( 1 + length×log(1+words) )

⏱ Time — freshness, on its own clock

Time is its own signal, independent of votes: a post starts at full freshness the moment it's published and decays from there, whether or not anyone has voted. This is what lets a brand-new post surface before it gets its first vote. Set the weight to 0 and age only reaches the feed through the timestamps of a post's votes.

▲ Votes

Recent votes, each decaying on its own half-life, so a burst of interest now outranks a stale favourite. Damped, so a landslide can't drown every other signal. Score is separate: it's the post's all-time approval, which keeps proven posts visible below actively-rising ones.

💬 Comments

How much active discussion lifts a post. Counts distinct people, not comments — one member replying fifty times is one person talking, not a crowd — and each commenter decays on the half-life below, so a thread that died yesterday stops rising however long it got. Default 0 = comments don't affect Rising.

📏 Length

Rewards longer, more substantial writing. Measured in words of prose — pictures and voice notes never count, so a one-word note carrying a big picture is not a long post. The boost saturates, so a 5,000-word wall doesn't bury a good 500-word piece. Default 0 = length doesn't affect Rising.

📄 Type

Promote a whole post type — e.g. set Article to 1.5 to rank articles half again as high as notes. This multiplies a post's whole score, so it's proportional, not a handout: a dead article still won't outrank a lively note. Pictures and voice notes ride inside a note or an article, so they follow their carrier's weight. 1 = neutral.

These two stack. Articles are long by definition, so raising Article and Length multiplies the same posts twice — an article at 1.5 with Length 0.3 ends up around 4–5× a short note, not 1.5×. The preview below shows the real total; trust it over the individual numbers.

Safe Browsing

Optional per-link reputation check. When a key is set, the relay checks links your members open against Google Safe Browsing over Tor — the URL never leaves the device (only 4-byte hash prefixes reach the relay, which forwards them to Google). This key is a relay secret: it is written to the relay config on this box only, never published or shared with members. Leave it off and members still get the local checks (punycode, dangerous schemes, tracker stripping).

Relays —

Publish extra relay mirrors for the community by onion address, then Publish relay list — it signs a kind-30078 event with your organizer key and sends it to the relay. Every app already tries these mirrors if the primary relay is unreachable, no app rebuild. Mirrors are additive for members: a published list can only ADD relays the app tries — it can never remove a relay a member already added or trusts themselves.

URL must be a v3 onion WebSocket address — ws:// or wss:// plus a 56-character base32 host ending in .onion. Leave the auth key blank for a public onion. Up to 5 relays.

Maintenance

Housekeeping to keep the dashboard fast and tidy. Nothing here touches live members or active invites.

Spent invite codes

Delete every invite that's expired or fully used. Active and partially-used codes are kept. This shrinks the invite list the dashboard loads each time you open it. A leftover code that was still mid-redemption simply re-issues a fresh credential — never a duplicate member.

Dashboard app files

The dashboard now caches its own code (about 360 KB) so it doesn't re-download on every page load — a big deal over Tor. It refreshes automatically whenever the organizer service restarts. Use this only if the interface looks stale or you've just deployed an update and want to force every device to pull the newest files.
